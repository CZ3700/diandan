## 1. 用户原话（2026-09-30）

> 后台需要新增经纪人账号权限（每个经纪人登录自己的账号只能查看和管理自己所绑定的艺人信息），然后需要对艺人有一个归属管理（比如哪些艺人归属哪个经纪人，在添加艺人的时候就需要填写绑定，如果是经纪人账号上传的艺人就默认绑定他自己，如果是超级管理员上传的艺人就分配绑定，未分配的就属于超管来直接管理，但是之后也可以再次分配），然后在管理后台查看订单的时候多一个页面可以查看每个艺人所收礼物的详情（包括时段选择、订单详情、成功完成的订单总额、待处理的订单笔数和详情等等），需要以清晰明了的方式来查账，并且可以导出表格（单人数据表格和单个经纪人旗下所有艺人数据以及全局数据表格都需要），然后你仔细理解我这个需求之后如果我还遗漏了什么的你可以给我补充上，但是最终的设计呈现不要太复杂，需要简单清晰明了，还有就是在我们管理后台的艺人管理页面可以备注艺人的基本信息（点开就能看到我们的备注信息，类似于联系方式和个人身份信息等等，仅平台超管账号可见）

拆成三个条目，按顺序交付：

| 条目 | 内容 |
|:--|:--|
| L3-11 经纪人账号与艺人归属 | 新角色“经纪人”；艺人归属（添加时绑定、之后可改派、未分配归超管直管）；经纪人只看得到、改得了自己名下的艺人 |
| L3-12 艺人收礼账目与导出 | 订单区新增“艺人账目”页：时段、每位艺人的已完成/待处理/退款、订单明细；导出单个艺人、单个经纪人全部艺人、全局三种表格 |
| L3-13 艺人私密备注 | 艺人资料里的私密备注（联系方式、身份信息等），只有超管能看能改 |

## 2. 需求整理

### 2.1 三种账号能做什么

“超管”指现有角色“工作室管理员”（`studio:owner`）。

| 功能 | 工作室管理员（超管） | 日常运营 | 经纪人（新） |
|:--|:--|:--|:--|
| 艺人：查看、添加、编辑资料 | 全部艺人 | 全部艺人 | **只有自己名下的** |
| 艺人：永久删除 | 可以 | 可以 | 不可以 |
| 艺人归属：添加时选经纪人、改派 | 可以 | 不可以（只看得到归属） | 不可以（自己添加的自动归自己） |
| 礼物、海报、店铺装修、支付、员工账号 | 按现有权限 | 按现有权限 | 都看不到 |
| 订单页（全部订单、处理订单、退款） | 按现有权限 | 按现有权限 | 看不到 |
| 艺人账目 | 全部艺人，可按经纪人筛选 | 全部艺人，可按经纪人筛选 | **只有自己名下的** |
| 粉丝写给艺人的私密留言 | 按现有订单权限 | 按现有订单权限 | **自己名下艺人收到的**，每条点开才显示，每次查看写审计 |
| 粉丝邮箱 | 不在账目中出现 | 不在账目中出现 | 任何情况下都看不到 |
| 导出表格 | 全局 / 某经纪人 / 某艺人 | 同左 | 自己名下全部 / 某艺人 |
| 艺人私密备注 | 查看、修改 | 看不到 | 看不到 |

经纪人登录后侧栏只有三项：**艺人**、**艺人账目**、**账号设置**。

### 2.2 艺人归属

- **添加艺人时**：
  - 超管：表单多一个“归属经纪人”下拉框，选项是“未分配（超管直管）”加所有经纪人，默认“未分配”；
  - 经纪人：没有这个下拉框，保存后自动归自己；
  - 日常运营：没有下拉框，添加的艺人为“未分配”，由超管之后分派。
- **改派**：超管在艺人编辑页改下拉框即可，立即生效。改派后，新经纪人能看到这位艺人的全部历史账目，原经纪人立即看不到。
- **未分配的艺人**：经纪人看不到；超管和日常运营照常管理（和现在一样）。
- **艺人列表**：超管和日常运营看到每位艺人的归属，可按“全部 / 未分配 / 某经纪人”筛选。
- **经纪人账号被暂停**：名下艺人不自动改动，列表里归属显示“（已停用）”，提醒超管改派。
- 每次绑定和改派都留痕（谁、什么时候、从谁改到谁），历史只追加、不能改。

### 2.3 艺人收礼账目

**入口**：订单区在“订单”“对账”旁边多一个“艺人账目”标签页；经纪人没有订单区，侧栏直接是“艺人账目”。

**页面只有两层**：

1. **总览**
   - 顶部：时段（今天 / 本周 / 本月 / 上月 / 自定义起止日期）、经纪人筛选（仅超管和运营）、艺人搜索；
   - 合计条：已完成金额与笔数、待处理金额与笔数、已退款金额；
   - 表格：每位艺人一行——艺人、归属经纪人、已完成（笔数/金额）、待处理（笔数/金额）、已退款、净收合计；点一行进入该艺人；
   - 按钮：“导出表格”（导出当前筛选范围：全局，或某经纪人全部艺人）。
2. **单个艺人**
   - 同样的合计条；
   - “待处理”列表在上：订单号、付款时间、礼物、数量、金额、状态（待准备/准备中/暂缓）、已等待天数；
   - “已完成”列表在下：订单号、付款时间、礼物、数量、金额、已退款、净额、送达时间；
   - 按钮：“导出该艺人”。
   - 有留言的礼物行带“查看留言”，点开才显示留言和署名，每次查看写审计（经纪人只能看自己名下艺人的；导出表格里永远没有留言）。

**统计口径**（页面上有一行“统计说明”）：

- 按**付款成功时间**落在所选时段内的礼物来算；金额和状态取当前最新（之后发生的退款也会扣掉）。
- **已完成**：已付款，这件礼物已送达，且没有被全额退款。金额 = 礼物金额 − 已成功退款。虚拟礼物付款即送达，直接算已完成。
- **待处理**：已付款，这件礼物还在待准备、准备中或暂缓，且没有被全额退款。
- **已退款**：已成功退到这件礼物上的金额；拒付败诉的订单整单算退回。退款处理中的金额单独注明，不算已退。
- **不计入**：未付款、已取消的订单。
- **笔数**按订单算（同一订单给同一艺人买了两件礼物算 1 笔），明细按礼物逐行列出。
- 一个订单里给不同艺人买的礼物，各算到各自艺人名下。
- **不同币种分开合计，永不相加**；TEST 支付产生的金额标“测试”，和真实收款分开。

**导出**：Excel 表格（.xlsx），两个工作表：

- “汇总”：艺人、经纪人、币种、已完成笔数与金额、待处理笔数与金额、已退款、净收合计；
- “明细”：订单号、付款时间、艺人、经纪人、礼物、类型、数量、单价、金额、已退款、净额、币种、状态、送达时间、已等待天数；
- 表头注明：导出范围、时段、时区、导出人、导出时间。

三种导出就是同一个按钮在不同范围下的结果：总览不筛选 = 全局；总览筛某经纪人 = 该经纪人全部艺人；艺人页 = 单个艺人。

### 2.4 艺人私密备注

- 艺人编辑页底部一个折叠区“私密备注（仅超管可见）”，点开才显示内容。
- 四个文字栏：**真实姓名**、**联系方式**（电话、邮箱、社交账号）、**身份信息**（证件类型与号码等）、**其他备注**。
- 显示“最后修改人 / 时间”，每次修改保留历史版本。
- **查看和修改都要求账号已开启两步验证，且本次登录输入过验证码或恢复码**（用户决定）；不满足时区域里只提示“开启两步验证后才能查看”。
- 日常运营和经纪人的页面上完全没有这个区域，接口也拒绝。

## 3. 我补充的内容

你没提到、但不定下来会出问题的：

1. **币种分开合计**：不同市场的订单可能是不同币种，直接相加会得出错误的总额。
2. **一单多艺人**：粉丝一次可以给几位艺人各买礼物，账目必须按礼物行归到各自艺人，不能按整单金额算。
3. **退款与拒付**：已完成金额要扣掉退款；拒付败诉（钱被银行退回）整单算退回。
4. **对账时区**：“今天/本月”从几点算起必须固定，否则不同人在不同地方导出的表对不上。用户定为北京时间（UTC+8，`Asia/Shanghai`），作为部署配置项，页面与表头都写明。
5. **导出不含粉丝个人信息**：表格里没有粉丝邮箱、署名和私密留言，只有订单号、礼物和金额。每次导出都写审计。
6. **经纪人不能删艺人**：删除不可恢复，只留给超管和运营。
7. **经纪人停用后的艺人**：不自动改归属，列表提示超管改派。
8. **待处理的“已等待天数”**：方便看出哪些礼物拖得久。
9. **私密备注只存文字**：不上传证件照片。证件照片的存储、访问和删除要求高得多，首发不做。
10. **私密备注加密保存、每次查看留痕**：沿用订单备注的做法（信封加密、查看写审计）。存艺人的身份信息前，建议经营方先取得艺人同意（上线前的隐私政策里要写明）。

## 4. 与现有规范的冲突，需要你知情

1. **SPEC §2.2 明确“不做外部经纪公司或多租户商户系统、不做自动分账”。**
   - 本方案的做法：经纪人是**超管在后台创建的员工账号**，只是能看到的艺人范围被限定；没有自助注册，也没有经纪人自己的店铺或收款。平台仍是唯一收款方。
   - 账目页只用于**内部对账**，不计算佣金、不结算、不打款。
   - 如果以后要按账目给经纪人或艺人分钱，那就是“分账”：支付服务商把平台型分账业务列为受限类目，需要重新评估，不在本方案里。
2. **2026-09-29 的决定“员工账号只保留工作室管理员和日常运营两个角色”（L3-10a）**：本方案新增第三个角色“经纪人”，按你这次的要求覆盖原决定。
3. **ADR-021 写的是“角色和权限模型不变”**：按艺人限定可见范围是新机制。
4. 按 SPEC §23.3，改变范围要写 ADR、升规范大版本、更新风险评估。开工第一步就做：ADR-022、SPEC 6.0.0、风险评估（导出和艺人身份信息两项）、上线计划和进度表。

## 5. 技术做法

**权限**（沿用现有“按权限键授权、数据库再校验一遍”的方式，不写角色名判断）：

| 权限键 | 含义 | 超管 | 运营 | 经纪人 |
|:--|:--|:--|:--|:--|
| `idols.assign` | 设置和改派艺人归属 | ✓ | | |
| `idols.private` | 查看和修改艺人私密备注 | ✓ | | |
| `management.assigned` | 在日常管理中心管理自己名下的艺人 | | | ✓ |
| `ledger.read` | 查看和导出全部艺人账目 | ✓ | ✓ | |
| `ledger.assigned` | 查看和导出自己名下艺人的账目 | | | ✓ |
| `ledger.messages` | 在账目里查看自己名下艺人收到的私密留言 | | | ✓ |

新角色 `studio:broker`，员工页可选“经纪人”，服务器命令 `admin-account.mjs` 同步补齐。

超管和运营在账目里看留言沿用现有的 `orders.message.read` 与语言授权；经纪人用 `ledger.messages`，范围限定为名下艺人，查看同样写审计并只在短时间内有效。

**数据库**（三个条目各一个迁移，down 都能回退）：

- `0057`（L3-11）：
  - 新表“艺人归属”，只追加：每次绑定或改派写一行，当前归属取最新一行；绑定的目标必须是经纪人角色的账号；
  - 替换 `0022` 的两个校验函数：原来只认 `management.direct`，现在多认一种情况——持有 `management.assigned`、操作是保存艺人，且是新建艺人或目标艺人归自己；
  - 经纪人新建艺人时，发布艺人的同一事务里写入归自己的归属；
  - 不给 `idols` 表加列，避免改动每次编辑都要碰的版本号。
- `0059`（L3-12）：只读查询需要的索引（`order_items.idol_id`、付款时间、退款分配），不新增业务表。账目是现有订单、付款、退款数据的只读汇总，不是第二个真相源。
- `0060`（L3-13）：私密备注表（密文、只追加的版本）和查看记录表，新的信封加密用途。
- 更正（2026-10-01）：原定 L3-12 用 0058，但 0058 已由远端协作者的海报特效（C-20261001）使用，L3-12、L3-13 各顺延一号。

**应用与界面**：

- 日常管理中心的艺人列表、保存、上传、操作查询按归属过滤；礼物、海报等分区对经纪人直接拒绝。
- 超管添加艺人时，先保存艺人，再写归属；第二步失败时艺人保持“未分配”，页面提示重试。未分配本来就归超管直管，所以不会出现越权。
- 账目页的数据由接口按权限范围返回，浏览器只负责显示和生成 Excel；导出也走同一个接口，并写审计。
- Excel 在浏览器本地生成，**不新增第三方依赖**：自己写一个最小的 .xlsx 生成模块（只用内联文字和数字，文字不会被当成公式执行），用单测解包核对，并在本机用 Excel 打开核对。
- 后台文案七种语言。

## 6. 实施顺序与验收

每个条目都按项目纪律来：先写失败测试 → 受影响单测 → 实际 PostgreSQL 专项脚本（含越权反例）→ 七语言 390×844 / 1440×900 浏览器验收（键盘、减少动态）→ `check:dev` → 提交推送 → 部署 stg 复核。

重点越权反例：

- 经纪人读、改、上传别人名下或未分配的艺人，接口和数据库都拒绝；
- 经纪人看不到礼物、海报、订单、员工和私密备注；
- 经纪人读别人名下或未分配艺人的留言被拒，每次读留言都有审计；
- 私密备注：运营、经纪人被拒；超管未开启两步验证或本次登录没输验证码时被拒；
- 经纪人的账目只含自己名下艺人；改派后原经纪人立即看不到；
- 运营不能改派、看不到私密备注；
- 导出内容与页面数字一致，不含粉丝个人信息；
- 金额核对：币种分开、退款扣减、拒付整单退回、一单多艺人拆分、未付款与已取消不计入。

工作量估计：L3-11 约一个会话，L3-12 约一个半到两个会话（含经纪人查看留言），L3-13 约半个会话。

## 7. 用户决定（2026-09-30）

1. **顺序**：先做已批准的 stg 正式构建，再依次做 L3-11 → L3-12 → L3-13；CI 回归穿插修。
2. **私密留言**：经纪人可以看自己名下艺人收到的私密留言，每条点开才显示，每次查看写审计；粉丝邮箱任何情况下都不给经纪人看，导出表格不含留言。
3. **对账时区**：北京时间 UTC+8。
4. **私密备注**：查看和修改都要求账号已开启两步验证、且本次登录经过验证码或恢复码。

## 8. 本方案不做

- 佣金计算、结算、打款、经纪人或艺人提现（属于“分账”）；
- 经纪人处理订单（准备、送达、退款）；
- 经纪人自助注册，艺人本人登录；
- 上传证件照片；
- 前台商城的任何变化。
