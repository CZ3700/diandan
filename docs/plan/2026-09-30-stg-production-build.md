## 1. 为什么要改

stg 上的商城和后台现在都跑 Next 开发服务器（`next dev`），带来两类问题：

- **验收缺口**：L3-10（后台内置账号）和 L3-09（应援凭证）都缺“正式构建下的浏览器验收”。
- **开发模式独有的故障**：
  - 重启后动态路由偶发全部 404，要再重启一次才恢复（09-29、09-30 各遇到一次）；
  - HMR 块加载失败（ChunkLoadError），09-30 部署前的开发日志里又出现一条；
  - 手机上的“1 Issue”徽标、开发版 React 触发的 CSP eval 提示。

stg 仍然是 TEST 环境：TEST 支付模拟器、TEST 收件箱、身份选择页和收件箱仍加 Basic Auth。本方案不把它变成正式 staging。

## 2. 目标形态

| 项目 | 现在 | 改后 |
|:--|:--|:--|
| 构建 | 部署时只构建依赖包，应用由 `next dev` 在运行时编译 | 部署时停机，构建四个应用（api、worker、admin、storefront），产物与 CI 一致 |
| 运行 | 两个 `next dev` 直接监听 `127.0.0.2:443`、`127.0.0.3:443` | 两个 `next start` 监听 `127.0.0.1:<已分配的后端端口>`，前面由实例自己的 Node TLS 代理占住原来的 `127.0.0.2/3:443` |
| 运行时层级 | development | test（编译产物是生产版 React、没有 HMR、订单页 CSP 不含 `unsafe-eval`） |
| Caddyfile、systemd 单元、DNS 预载 | — | **都不改** |

做法要点：

- **不按实例构建**：两个应用都没有 `NEXT_PUBLIC_*`，除两个静态文件外路由全是动态的，`next start` 启动时会重新读 `next.config.ts`，实例地址都在运行时读取。构建时不带任何 `FAN_SUPPORT_*` 变量，和 CI、Dockerfile 一致。
- **寻址**：复用已有的 `startLocalProxy`，它会覆盖 Host、X-Forwarded-Host、X-Forwarded-Proto；两个应用的 `request-origin.ts` 本来就按“私有监听 + 代理”设计。仓库里已经有同样结构跑正式构建后台的先例（`apps/api/scripts/production-admin-oidc-next.mjs`）。
- **开关**：实例配置新增可选字段 `webMode: "PREBUILT"`，用 `pnpm local:web-mode --instance stg --mode PREBUILT|DEVELOPMENT` 切换，下次启动生效，写法照搬 `local:admin-sign-in`。不写这个字段就是现在的开发模式，本地实例不受影响。
- **启动时绝不编译**：构建不存在，或者构建戳记的版本不等于当前 `HEAD`，就直接失败并提示先构建。这样“构建失败却照常重启”的问题不会再发生。
- **构建命令**：新增 `local:build-web`。实例运行时拒绝执行；退出码如实返回，不再有 `| tail` 吞掉失败的问题；成功后才写戳记。
- **商城不再拿到后台凭据**：现在开发模式会把后台 access key 也传给商城进程，新形态按已有先例只给商城留 `ADMIN_ORIGIN`。

## 3. 唯一的阻断点：配置校验

`packages/config/src/server-config.ts` 的 `resolveAdminRuntimeConfig` 规定：`LOCAL_ACCOUNT` 只要不在 development 层，就按正式模式校验，要求 staging/production 层、`NODE_ENV=production`、公网 HTTPS 内部 API。stg 的 test 层三条都不满足，编译后的后台根本起不来。

改法：只给 `LOCAL_ACCOUNT` 在 test 层开一个窄口子，条件同时满足才放行：

- 层级为 test、`NODE_ENV=test`；
- 站点地址为公网 HTTPS；
- 内部 API 为回环 HTTP。

正式部署（staging/production）不可能落进这个组合，`LOCAL_OIDC` 和 `TEST` 在 test 层仍然拒绝。

这是改共享配置包，Mario 那边会同步到，完成后会在进度表写明。

## 4. 实施步骤（先写失败测试）

1. **测试先行**：

   - 实例：模式判定、`PREBUILT` 必须配 `LOCAL_ACCOUNT`、只启动不构建、商城环境里没有后台凭据、构建缺失或戳记过期时在启动任何进程之前失败；
   - 代理：可以绑定 `127.0.0.2`，拒绝非回环地址；

2. **实现**：配置包、实例配置与切换命令、Web 启动分支（开发模式代码不动）、代理绑定地址、构建命令。
3. **本机验证**：受影响测试、`check:dev`；在本机用编译后的后台，在 test 层重跑 L3-10 的登录、账号设置、员工账号三套浏览器用例。

## 5. 风险与回滚

**风险**

- **构建耗时和内存没有实测**：2 核 4GB 的机器，停机时间约等于构建时间。首次构建用 `/usr/bin/time -v` 记录。先停实例再构建，腾出两个开发服务器占的内存，并用 `--concurrency=1`。真的内存不够再考虑加 swap。不建议换构建工具，也不建议在别处构建，以免和 CI 不一致。
- **报错可见性下降**：正式模式下没有 `next-development.log`，浏览器端报错不再回传到服务器，React 报错会压缩成错误码。
  - 排查改靠 Playwright 采集控制台和页面报错；
  - 真机问题临时切回 `DEVELOPMENT` 复现。
- **部署瞬间**：还开着的旧页面可能遇到一次块加载失败，刷新即可。

**回滚**

1. **最快**：`pnpm local:web-mode --instance stg --mode DEVELOPMENT`，然后重启。同一版本回到开发服务器，不用重新构建。
2. **回退代码**：必须先切回 `DEVELOPMENT`（这一步会删掉 `webMode` 字段），或者从冷备份恢复实例配置，再 reset 到旧版本。原因是旧代码的配置校验遇到不认识的字段会拒绝启动。
3. **冷备份**：沿用已有约定，版本号写在 `.revision` 文件里。Caddyfile 不变，不需要备份。

## 6. 需要你决定的问题

1. **这样算不算关闭“正式构建验收”缺口？**
   - 编译产物是正式的，但 stg 运行时是 test 层，`LOCAL_ACCOUNT` 在 staging/production 下的那套正式配置校验在 stg 上跑不到，只有单元测试覆盖。
   - **我的建议**：记为“正式编译产物的浏览器验收已完成”；“正式配置路径”这一半留到正式 staging（R1）时关闭，不在 stg 上硬凑。
2. **test 层放开哪些登录方式？**
   - **建议**：只放开 `LOCAL_ACCOUNT`。stg 已经在用内置账号，没有必要让编译模式再支持身份选择页。
3. **构建时机**
   - **建议**：部署时“停机 → 构建 → 启动”。
   - 不采用“每次启动都构建”（先例的做法）：每次重启都要付构建成本，而且是在整套服务运行时构建。
   - 不采用“每个版本独立构建目录”：几乎不停机，但复杂度明显更高，对 TEST 环境不值得。
4. **启动时是否强制核对构建戳记？**
   - **建议**：核对，实现成本很低。“构建失败却照常重启”这类问题我们已经遇到过。
5. **是否新增服务器事件日志？**
   - 内容：只记录通过结构化日志校验的事件行，写入私有文件（权限 0600、限制大小），其余输出照旧丢弃。目的是弥补开发日志没有之后，服务端报错完全看不到的问题。
   - **建议**：随本项一起做，改动很小。
6. **远程走查脚本**
   - `remote-test-walkthrough.mjs` 还在用 L3-10 之前的 OIDC 登录表单，现在已经跑不通。
   - **建议**：另开一个小项处理，不阻塞本项。本项的验收用上面列出的专项脚本。
