# F1-3 首页改版、四分类、价格直显第二阶段：实现设计

> 日期：2026-09-26 · 依据：V2 方案 §4 第 2、3 项，ADR-017 及其增补，ADR-019，规范 §5.1、§5.2、§5.5.1，`docs/plan/v2-friction-items.md` 第 2 项；范围与顺序见 `docs/handoff/2026-09-26-core-features-first.md`（已获批准）
> 前置：F1-2 已完成（迁移头 0039）。本项不需要数据库迁移

## 1. 结论一句话

两个公开目录接口（内容目录 `GET /api/v1/gift-browse` 与带价目录 `GET /api/v1/gifts`）增加 `kind` 筛选并在结果里带出每个礼物的分类；首页改为满屏偶像海报首屏，海报下放四个分类磁贴链接到 `/gifts?kind=`；只发布一个市场和一个币种时，`/gifts` 与首页目录直接显示价格，规范 URL 与站内链接不再携带这个隐含作用域，页眉抽屉和页脚隐藏"选择地区"。页壳和内容仍先于商业上下文流式输出。

## 2. 分类数据从哪里来

`gift_kind` 不在 `gifts` 表上，而是按礼物修订存放，按修订的 `profile_version` 分三种情况：

| 修订 | 分类来源 |
|:--|:--|
| v3（日常发布） | `daily_publication_revisions.document->>'giftKind'`（`gift_revision_id` 唯一） |
| v2（礼物商务资料） | `gift_revision_profiles.gift_kind`（`gift_revision_id` 为主键） |
| v1（早期修订） | 没有分类 |

取值规则与 `order-line-gift-kind.ts` 相同：先取日常发布文档，再取修订资料，都没有时为 NULL。两个都是按唯一键的 LEFT JOIN，不需要迁移或新索引。

v1 修订没有分类，按分类筛选时不会出现，只在"全部"里出现。这是既有数据的真实状态，不做猜测性回填。

## 3. 合同

| 合同 | 变更 |
|:--|:--|
| `giftBrowseQuerySchema` | 新增 `kind: giftKindSchema.optional()` |
| `giftDiscoveryQuerySchema` | 新增 `kind: giftKindSchema.optional()`；`changeGiftDiscoveryQuerySchema.changes` 新增 `kind`（可置 null），改变分类回到第 1 页 |
| `publishedGiftViewSchema`（含 legacy） | 新增 `giftKind: giftKindSchema.nullable().optional()`。目录读取（两个接口）总会带上：值为分类，NULL 为无分类的早期礼物；其他读取路径（详情内容等）不带此字段 |
| `giftBrowseSnapshotSchema`（内部） | 新增与 `items` 等长的 `giftKinds` |
| `giftDirectorySnapshotSchema` 条目（内部） | 新增 `giftKind` |

把 `giftKind` 放在礼物视图上而不是另包一层：ADR-019 把分类定为与 `category` 同级的展示分类，日常发布文档里两者本来就并列；而内容目录的条目就是视图本身，另包一层会改动所有消费方与夹具。字段可选，所以不影响现有的其他读取路径。

OpenAPI 与 `contracts.schema.json` 由 `contracts:generate` 重新生成（查询参数自动派生）。

## 4. 持久化

- 两条目录 SQL 在已选出的发布修订上 LEFT JOIN 日常发布文档与修订资料，计算 `gift_kind`：
  - 内容目录：`AND ($6::text IS NULL OR gift_kind = $6)`，页内结果返回 `[id, gift_kind]` 对。
  - 带价目录：`candidates` 带出 `gift_kind`，`filtered` 增加 `AND ($11::text IS NULL OR gift_kind = $11)`，窗口行带出 `giftKind`。
  - 新参数追加在参数表末尾，原有参数位置不变。
- 对 v3 记录，仓储核对 SQL 得到的分类与记录里发布文档的 `giftKind` 一致，不一致视为目录不可用。
- `versionState` 不变：修订资料和日常文档都按修订不可变，发布头变化已经改变目录版本。

## 5. 应用层与 API

- 两个用例把快照里的分类附到投影出的礼物视图上；有 `kind` 筛选时，每个条目的分类必须等于筛选值，否则返回 `CATALOG_UNAVAILABLE`（与现有的 `category` 复核同一口径）。
- 两个 API 路由的参数白名单加入 `kind`；路由层同样复核条目分类。
- 规划器 `createGiftDiscoveryPlan` 原样传递 `kind`。

## 6. 前台

### 6.1 URL 状态与筛选

- `kind` 进入两个目录的 URL 状态（规范 §5.5.1）：`prepareGiftBrowse`、`prepareGiftQuery` 解析它，分页、筛选与重置链接保留或清除它，改变分类回到第 1 页。
- 筛选工具栏在"分类"前加"礼物类型"选择（全部 + 四类）；已应用筛选的摘要显示类型。
- 任何带 `kind` 的目录页都是筛选页：`noindex`，canonical 保留 `kind`（与 `category` 同一口径）。
- 目录卡片在标题上方显示分类小标签（四类才显示，OTHER 与无分类不显示）。

### 6.2 首页

内容顺序按规范 §5.2 调整为：满屏海报 → 四分类磁贴 → 偶像选择 → 礼物目录 → 政策链接 → 送礼流程 → 信任 → 最终 CTA。

- **满屏海报**：
  - 桌面（≥48rem）：已发布的桌面构图铺满首屏（视口高度减去页头），按焦点裁切；品牌眉题、短标题、正文、单一 CTA 与主偶像署名叠在左下，底部与左侧有渐变遮罩保证对比度。
  - 手机：图框按已发布手机构图的真实宽高比显示、不裁切（CI 浏览器脚本 `storefront-browser.mjs` 要求图框比例等于构图比例，图片失败时占位尺寸不变）；文字区上移压在图片底部的渐变上，与图片连成一张海报。
  - 进入动效、减少动态效果与图片失败回退沿用现有实现。
- **四分类磁贴**：虚拟礼物 / 实物礼物 / 艺人心愿 / 周边，每块是一个链接（序号、类型名、一句说明、箭头），指向 `/gifts?kind=…` 并保留当前导航上下文（显式市场等）。四块总是显示，不依赖商业上下文或目录读取，所以随页壳一起输出。某类暂时没有礼物时，目录页显示已有的空结果状态与重置入口。
  - 类型名沿用礼物详情已有的 `giftKind*` 文案，粉丝在磁贴、筛选、卡片和详情看到同一个名字；ADR-019 要求不使用"打赏/捐赠"措辞。
  - 说明文案新增，不得暗示礼物寄给粉丝本人（规范 §5.5）。

### 6.3 价格直显第二阶段

**流式结构**：目录区在自己的 Suspense 边界里等待商业上下文，边界的回退内容就是现有的纯内容目录。

- 上下文确认唯一市场：渲染带价目录（`GET /api/v1/gifts`，作用域为这对市场/币种）。
- 多个市场、上下文失败或带价目录读取失败：渲染纯内容目录，与现在相同。
- 上下文慢：先看到纯内容目录，上下文到达后原位替换为带价目录。

这样页壳、首屏海报、磁贴、偶像轨道和目录内容都不等待商业上下文，满足 ADR-017 增补的流式保障。代价是每次渲染多一次内容目录读取；首页本来就提前发起这次读取。

- `/gifts`：带价时使用完整筛选（排序、类型、分类、价格区间、可售状态）。
- 首页：带价时仍用首页的简洁工具栏（类型 + 分类 + 分页），卡片显示起价。
- 艺人页目录（第一阶段已带价）改用同一套"隐含作用域"链接规则。

**隐含作用域**：唯一市场推导出的作用域只用于读取价格，不写进 URL。

- 站内分页、筛选、重置和卡片链接不携带隐含的 `market`/`currency`；
- URL 里显式写了市场和币种（包括与隐含作用域相同的值）时仍视为显式选择，行为不变。

**规范 URL**：SEO 身份（`createSeoIdentity`）接受隐含作用域。

- URL 中的市场/币种等于隐含作用域时，canonical 去掉它们，于是 `/gifts` 与 `/gifts?market=…&currency=…` 收敛到同一个 canonical。
- 无作用域的 `/gifts` 在唯一市场时是可索引的带价目录（目前因为缺作用域而 noindex）。
- 适用于 `/gifts`、礼物详情与艺人页。

**地区入口**：页眉抽屉里的地区提示与链接、页脚的"地区与币种"链接改为各自的 Suspense 插槽。

- 上下文确认唯一市场时不渲染；多个市场或上下文失败时照常显示。
- 回退为空，所以单一市场站点上不会先闪出链接再消失。
- `/region` 页本身保留，显式选择仍然可用。

## 8. 提交拆分

1. **F1-3a**：`kind` 筛选贯通 API（合同与 OpenAPI → 持久化 → 应用 → API 路由）。真实 PostgreSQL 验证两条 SQL。
2. **F1-3b**：前台 `kind` URL 状态、筛选与卡片标签；首页满屏海报与四分类磁贴；七语言文案。
3. **F1-3c**：价格直显第二阶段（带价目录的流式结构、隐含作用域链接与 canonical、地区入口）。
4. 本机浏览器验收，然后登记进度并写交接。

## 9. 验证计划

- **单元与组件测试**（先写失败测试）：
  - 合同：两个查询的 `kind` 解析；
  - SQL 构造器：参数表与筛选子句；
  - 仓储：分类配对与 v3 文档核对；
  - 应用层与路由：分类附加与复核；
  - 前台：URL 状态、链接、磁贴、卡片标签、SEO 身份；
  - 流式测试：上下文慢时先出纯内容目录，唯一市场时替换为带价目录；上下文失败时保持纯内容；页眉页脚地区入口按上下文显示或隐藏。
- **真实 PostgreSQL**：`gift-browse-postgres.mjs` 与 `postgres-catalog-directory.mjs` 增加分类筛选用例，覆盖 v2 资料、v3 文档、v1 无分类，以及筛选在分页之前生效。
- **浏览器**：本机没有 S3，完整本地体验跑不起来。临时起一个假 API 夹具服务（只实现首页与目录用到的读取接口，图片由夹具提供），让 Next 前台指向它，用本机 Chrome 验证：
  - 两种尺寸：390×844、1440×900；
  - 语言：en、zh-CN、th、vi、es；
  - 状态：唯一市场带价、多市场不带价、上下文失败、空分类，以及键盘焦点与减少动态效果。

  夹具与截图放在 `output/checks/f1-03/`，不入库。已有的 CI 浏览器脚本如果依赖改动过的首页结构，同步调整选择器，等 CI 验证。
- **门禁**：`pnpm check:dev`；`contracts:generate` 后的产物新鲜度测试。

## 10. 不在本项范围

- 分类计数（磁贴上显示各类数量）：需要额外的聚合读取，等有真实数据后再定。
- 规范 §5.1 的桌面透明覆盖式页头：属于全站页头改动，不随本项调整。
- 多市场时的地理预选（附录第 2 项的后续设想）：仍需显式选择。
