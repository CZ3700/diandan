# ADR-022：后台新增经纪人员工账号、艺人归属、艺人收礼账目与艺人私密备注

> 状态：Accepted
> 日期：2026-09-30
> 决策者：用户（经营方）；Claude（Windows 端）整理方案
> 关联：进度条目 L3-11、L3-12、L3-13；风险 R-02、R-10、R-18、R-19；修改 SPEC §2.2、§3.1（6.0.0），覆盖 L3-10a“员工账号只保留两个角色”，补充 ADR-021“角色和权限模型不变”

## 背景

用户 2026-09-30 要求（原话见[方案](../plan/2026-09-30-brokers-ledger-private-notes.md)第 1 节）：

- 后台新增经纪人账号，经纪人只能查看和管理自己名下的艺人；
- 艺人有归属：添加时绑定，经纪人添加的归自己，超管添加的由超管分配，未分配的归超管直管，之后可以改派；
- 订单区新增按艺人查看收礼情况的页面，可选时段，能导出单个艺人、单个经纪人全部艺人、全局三种表格；
- 艺人管理页可以写私密备注（联系方式、身份信息等），仅平台超管可见。

已核实的现状：

- SPEC §2.2 把“外部经纪公司或多租户商户系统”“自动分账”列为不做；
- 后台只有“工作室管理员”“日常运营”两个标准角色（L3-10a），权限完全按权限键判断，除语言授权外没有任何按对象限定范围的机制；
- 礼物不绑定艺人，粉丝加购时选收礼艺人，订单行记录 `order_items.idol_id`；订单可能是不同币种；
- 平台是唯一收款方（merchant of record），不向艺人分账。

## 决策

在平台内部员工账号体系内新增“经纪人”角色与按艺人限定的可见范围，新增只读的艺人收礼账目与导出，新增只有超管可见的艺人私密备注。平台仍是唯一收款方，账目只用于内部对账。

1. **经纪人是员工账号**：只能由持有员工管理权限的账号在后台或服务器命令创建，角色键 `studio:broker`；没有自助注册，没有经纪人自己的店铺、收款或结算。艺人本人仍不能登录（SPEC §3.1 不变）。
2. **经纪人的范围**：日常管理中心里只能查看、添加、编辑自己名下的艺人（不能删除），查看自己名下艺人的收礼账目并导出，查看自己名下艺人收到的私密留言（每条点开才显示，每次写审计）。看不到礼物、海报、店铺装修、支付、订单处理、员工账号、私密备注和粉丝邮箱。
3. **艺人归属**：只追加的归属记录，当前归属取最新一条；只有持 `idols.assign` 的账号（超管）能设置或改派；经纪人新建的艺人在发布同一事务里归自己；日常运营新建的艺人为未分配。未分配的艺人由超管和日常运营照常管理。改派后账目按当前归属显示（新经纪人看到全部历史，原经纪人立即看不到）。
4. **授权方式**：沿用“权限键 + 仓储层授权 + 数据库再校验”。新增权限键 `idols.assign`、`idols.private`、`management.assigned`、`ledger.read`、`ledger.assigned`、`ledger.messages`，分配见方案第 5 节。数据库里原来只认 `management.direct` 的两个日常管理校验函数，新增“持 `management.assigned` 且目标是新建艺人或名下艺人”的分支。
5. **收礼账目**：现有订单、付款、退款数据的只读汇总，不是第二个真相源。按付款成功时间落入时段的礼物行统计；已完成 = 已付款、已送达、未全额退款，金额扣除已成功退款；待处理 = 已付款、待准备/准备中/暂缓、未全额退款；拒付败诉整单算退回；未付款与已取消不计入；按币种分开合计，TEST 金额单独标注。时段按北京时间（UTC+8）划分（用户决定），时区为部署配置项。
6. **导出**：浏览器本地生成 .xlsx（汇总与明细两个工作表），数据来自与页面相同的受权接口，每次导出写审计。表格不含粉丝邮箱、署名和私密留言。不新增第三方依赖。
7. **私密备注**：四个文字栏（真实姓名、联系方式、身份信息、其他备注），信封加密、只追加版本；只有持 `idols.private` 的账号（超管）能查看和修改，并且要求账号已开启两步验证、本次登录经过验证码或恢复码（用户决定，只作用于这一项）；每次查看写审计。不上传证件照片；不进入日志、分析、导出或普通 DTO。

## 考虑的方案

| 方案 | 优点 | 缺点/风险 | 为什么选择或拒绝 |
|:--|:--|:--|:--|
| A. 员工账号 + 按艺人限定范围（本决定） | 复用现有账号、会话、审计；平台仍是唯一收款方 | 需要在日常管理中心和数据库校验里加范围分支 | 满足用户要求且不引入商户体系 |
| B. 经纪人作为外部商户（多租户） | 经纪人可自管店铺与收款 | 违反 SPEC §2.2；支付服务商受限类目（平台型分账） | 拒绝 |
| C. 只在界面上隐藏其他艺人 | 实现快 | 接口和数据库不设防，等于没有权限 | 拒绝 |
| D. 给 `idols` 表加归属列 | 查询简单 | 每次改归属都要推进艺人版本号，与日常编辑冲突；没有历史 | 拒绝，改用独立的只追加表 |

## 后果

- SPEC 升到 6.0.0：§0.5 记录本次变更；§2.2 注明平台内部的经纪人员工账号不属于“外部经纪公司或多租户商户系统”；§3.1 新增经纪人角色。
- 员工账号页的标准角色从两个变为三个，覆盖 L3-10a 的决定。
- 新增迁移（0057 起，每个条目一个）、合同、七语言后台文案、实际 PostgreSQL 专项脚本（含越权反例）与浏览器验收。
- 风险评估：R-02 补充账目导出与经纪人读留言；新增 R-18（艺人私密备注泄露）与 R-19（经纪人越权看到其他艺人数据）。
- **明确不做**：佣金计算、结算、打款、经纪人或艺人提现（属于分账，以后如要做需重新评估支付服务商资质）；经纪人处理订单；经纪人自助注册；艺人登录；证件照片上传；前台商城变化。

## 验证与回退

- 验证：每个条目先写失败测试；实际 PostgreSQL 专项脚本覆盖越权反例（经纪人读改他人或未分配艺人、读他人留言、访问礼物/订单/备注；运营改派或读备注；未两步验证的超管读备注）；账目金额核对（币种分开、退款扣减、拒付整单、一单多艺人、未付款与取消不计入）；导出内容与页面一致且不含粉丝个人信息；七语言双端浏览器验收；`check:dev`；部署 stg 复核。
- 回退：三个迁移各自可 down（有归属、备注历史时拒绝回退，避免静默丢数据）；代码回退到上一版本即恢复为两个标准角色。经纪人账号可先暂停再回退。
