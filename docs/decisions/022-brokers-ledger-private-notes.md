# ADR-022：后台新增经纪人员工账号、艺人归属、艺人收礼账目与艺人私密备注

> 状态：Accepted
> 日期：2026-09-30
> 决策者：用户（经营方）；Claude（Windows 端）整理方案
> 关联：进度条目 L3-11、L3-12、L3-13；风险 R-02、R-10、R-18、R-19；修改 SPEC §2.2、§3.1（6.0.0），覆盖 L3-10a“员工账号只保留两个角色”，补充 ADR-021“角色和权限模型不变”

## 背景

用户 2026-09-30 要求（原话见[方案](../plan/2026-09-30-brokers-ledger-private-notes.md)第 1 节）：

- 后台新增经纪人账号，经纪人只能查看和管理自己名下的艺人；
- 艺人有归属：添加时绑定，经纪人添加的归自己，超管添加的由超管分配，未分配的归超管直管，之后可以改派；
- 订单区新增按艺人查看收礼情况的页面，可选时段，能导出单个艺人、单个经纪人全部艺人、全局三种表格；
- 艺人管理页可以写私密备注（联系方式、身份信息等），仅平台超管可见。

已核实的现状：

- SPEC §2.2 把“外部经纪公司或多租户商户系统”“自动分账”列为不做；
- 后台只有“工作室管理员”“日常运营”两个标准角色（L3-10a），权限完全按权限键判断，除语言授权外没有任何按对象限定范围的机制；
- 礼物不绑定艺人，粉丝加购时选收礼艺人，订单行记录 `order_items.idol_id`；订单可能是不同币种；
- 平台是唯一收款方（merchant of record），不向艺人分账。

## 决策

在平台内部员工账号体系内新增“经纪人”角色与按艺人限定的可见范围，新增只读的艺人收礼账目与导出，新增只有超管可见的艺人私密备注。平台仍是唯一收款方，账目只用于内部对账。

1. **经纪人是员工账号**：只能由持有员工管理权限的账号在后台或服务器命令创建，角色键 `studio:broker`；没有自助注册，没有经纪人自己的店铺、收款或结算。艺人本人仍不能登录（SPEC §3.1 不变）。
2. **经纪人的范围**：日常管理中心里只能查看、添加、编辑自己名下的艺人（不能删除），查看自己名下艺人的收礼账目并导出，查看自己名下艺人收到的私密留言（每条点开才显示，每次写审计）。看不到礼物、海报、店铺装修、支付、订单处理、员工账号、私密备注和粉丝邮箱。
3. **艺人归属**：只追加的归属记录，当前归属取最新一条；只有持 `idols.assign` 的账号（超管）能设置或改派；经纪人新建的艺人在发布同一事务里归自己；日常运营新建的艺人为未分配。未分配的艺人由超管和日常运营照常管理。改派后账目按当前归属显示（新经纪人看到全部历史，原经纪人立即看不到）。
4. **授权方式**：沿用“权限键 + 仓储层授权 + 数据库再校验”。新增权限键 `idols.assign`、`idols.private`、`management.assigned`、`ledger.read`、`ledger.assigned`、`ledger.messages`，分配见方案第 5 节。数据库里原来只认 `management.direct` 的两个日常管理校验函数，新增“持 `management.assigned` 且目标是新建艺人或名下艺人”的分支。
5. **收礼账目**：现有订单、付款、退款数据的只读汇总，不是第二个真相源。按付款成功时间落入时段的礼物行统计；已完成 = 已付款、已送达、未全额退款，金额扣除已成功退款；待处理 = 已付款、待准备/准备中/暂缓、未全额退款；拒付败诉整单算退回；未付款与已取消不计入；按币种分开合计，TEST 金额单独标注。时段按北京时间（UTC+8）划分（用户决定），时区为部署配置项。
6. **导出**：浏览器本地生成 .xlsx（汇总与明细两个工作表），数据来自与页面相同的受权接口，每次导出写审计。表格不含粉丝邮箱、署名和私密留言。不新增第三方依赖。
7. **私密备注**：四个文字栏（真实姓名、联系方式、身份信息、其他备注），信封加密、只追加版本；只有持 `idols.private` 的账号（超管）能查看和修改，并且要求账号已开启两步验证、本次登录经过验证码或恢复码（用户决定，只作用于这一项）；每次查看写审计。不上传证件照片；不进入日志、分析、导出或普通 DTO。

## 考虑的方案

| 方案 | 优点 | 缺点/风险 | 为什么选择或拒绝 |
|:--|:--|:--|:--|
| A. 员工账号 + 按艺人限定范围（本决定） | 复用现有账号、会话、审计；平台仍是唯一收款方 | 需要在日常管理中心和数据库校验里加范围分支 | 满足用户要求且不引入商户体系 |
| B. 经纪人作为外部商户（多租户） | 经纪人可自管店铺与收款 | 违反 SPEC §2.2；支付服务商受限类目（平台型分账） | 拒绝 |
| C. 只在界面上隐藏其他艺人 | 实现快 | 接口和数据库不设防，等于没有权限 | 拒绝 |
| D. 给 `idols` 表加归属列 | 查询简单 | 每次改归属都要推进艺人版本号，与日常编辑冲突；没有历史 | 拒绝，改用独立的只追加表 |

## 后果

- SPEC 升到 6.0.0：§0.5 记录本次变更；§2.2 注明平台内部的经纪人员工账号不属于“外部经纪公司或多租户商户系统”；§3.1 新增经纪人角色。
- 员工账号页的标准角色从两个变为三个，覆盖 L3-10a 的决定。
- 新增迁移（0057 起，每个条目一个）、合同、七语言后台文案、实际 PostgreSQL 专项脚本（含越权反例）与浏览器验收。
- 风险评估：R-02 补充账目导出与经纪人读留言；新增 R-18（艺人私密备注泄露）与 R-19（经纪人越权看到其他艺人数据）。
- **明确不做**：佣金计算、结算、打款、经纪人或艺人提现（属于分账，以后如要做需重新评估支付服务商资质）；经纪人处理订单；经纪人自助注册；艺人登录；证件照片上传；前台商城变化。

## 增补：L3-11 实现约定（2026-09-30）

- **经纪人角色的权限**：`management.assigned`、`ledger.assigned`、`ledger.messages`，外加四个媒体权限（`content.media.upload/read/process/rights`）。日常发布流程以提交人的会话处理照片，没有这四个权限经纪人就无法添加或更换名下艺人的照片。这些接口只能按素材 ID 访问、没有列表（风险记入 R-19）。
- **标准角色的权限清单**放在合同包（`adminStandardRolePermissions`），服务器命令按它授予：工作室管理员不持有三个“只限名下”的权限键，日常运营另外不持有 `idols.assign` 和 `idols.private`。迁移 0057 只登记它的校验函数用到的 `idols.assign`、`management.assigned`，其余四个键随 L3-12、L3-13 的迁移登记。已有环境更新后执行 `admin-account.mjs sync-roles`。
- **一个账号同时有经纪人和其他角色**：只要持有 `management.direct`，就按“管理全部艺人”处理，新建的艺人不自动归自己。员工页的角色说明里写明这一点。
- **接口里的经纪人标识**是员工身份 ID（`admin_identities.id`）加显示名和“是否有效”，不含登录名或联系方式。艺人列表每一项都带归属（未分配为 null）；经纪人的列表只含自己名下的艺人。
- **改派**是单独的命令 `ASSIGN_ARTIST`（只需 `idols.assign`），带“编辑页看到的原归属”，与当前不一致时拒绝，重复提交同一归属不写新记录。编辑已有艺人时改下拉框立即保存；新建艺人时，选择在艺人发布成功后由页面提交，失败则艺人保持未分配并提示。
- **数据库**：`idol_assignments` 只追加，每行记录前后归属、操作人、会话和审计记录；写入由触发器校验（顺序、前一归属、审计记录、目标是有效的经纪人、`idols.assign` 或“本人运行中的新建艺人操作”）。0022 的两个函数改为调用 `assert_management_scope`：持 `management.direct` 的账号走原来的检查，否则要求 `management.assigned` 且操作是保存名下艺人或新建艺人。
- **改派后原经纪人排队中的修改**：worker 领取时发现已无权限，记为“需要重新授权”的失败，不会发布。

## 增补：L3-12 实现约定（2026-10-01）

- **迁移序号**：0058 已由海报特效（C-20261001）使用，账目用 **0059**。（更正 2026-10-01：0060、0061 随后由心愿绑定与展馆 ADR-023 使用，私密备注用 0062。）
- **0059 的内容**：登记 `ledger.read`、`ledger.assigned`、`ledger.messages`（`ON CONFLICT DO NOTHING`：跑过 `sync-roles` 的库里已有这些键）；三个只读索引（成功付款时间、订单行的艺人、退款行）；只追加的导出回执表 `artist_ledger_exports`（范围、时段、时区、行数，触发器核对对应审计 `ARTIST_LEDGER_EXPORT`，并在数据库再校验一次导出权限：`ledger.read` 可导出任意范围，只有 `ledger.assigned` 的账号只能导出自己或自己名下的某位艺人）；用 `CREATE OR REPLACE` 给 0031 的 `assert_admin_order_receipt_authority` 加一个经纪人分支。down 逐字恢复 0031 的函数，存在导出回执时拒绝回退（55000）。
- **口径**：一行礼物进入账目，当且仅当它所在订单的成功付款时间落在所选时段内（数据库约束保证已取消的订单都没有付款）。付款后履约被取消且未全额退款的行归为“已关闭”，不算已完成也不算待处理，但仍计入净收合计，并在艺人页“已退款或已关闭”列表里逐行列出，不会凭空消失。已退款金额取成功退款并以行金额为上限；拒付败诉时整行记为退回（此前的部分退款不重复计算）。“已等待天数”按付款至今的整 24 小时计。
- **时段**：由服务器按部署配置 `FAN_SUPPORT_LEDGER_TIME_ZONE`（缺省 `Asia/Shanghai`）在数据库里换算：预设“今天/本周（周一起）/本月/上月”，自定义为含首尾的日期、最长 366 天。浏览器只传预设名或日期，不传时区。
- **单条语句**：合计、艺人行和明细由同一条 SQL 在同一个快照里算出，所以页面上的合计与行永远一致；导出与页面走同一个查询。明细最多 10000 行，超出时返回“已截断”并在页面和表格里注明。
- **范围**：持 `ledger.read` 看全部艺人并可按经纪人或“未分配”筛选；只有 `ledger.assigned` 的经纪人被限定为 `idol_current_broker(艺人)=自己`，别人的艺人按“不存在”处理（不泄露存在与否）。改派后原经纪人立即看不到（包括已经准备好、尚未确认的留言读取）。
- **读留言**：沿用订单页“先写审计与五分钟访问记录、再在应用层解密、最后复核”的流程和 `admin_order_private_accesses` 表。经纪人分支：持 `ledger.messages`、礼物行已付款、艺人当前归自己，且留言**没有被工作室拒绝或删改**（`moderation_status` 不是 REJECTED/REDACTED）；待审核和已通过的都可以看，不要求语言授权。其他账号走订单页原规则（`orders.read`+`orders.message.read`、所用界面语言的授权，留言语言不同时需要 `orders.message.triage`）。数据库触发器按同样的顺序复核，直接写库绕不过去。
- **导出**：浏览器本地生成 .xlsx（`apps/admin/src/management-ledger/xlsx.ts`，不新增依赖；文字一律是内联字符串，以“=”开头也不会被当成公式；金额是按币种小数位的精确小数）。两个工作表“汇总”“明细”，表头写明范围、时段、时区、导出人、导出时间。导出响应的行结构里没有留言相关字段，所以表格里不可能出现留言、署名或邮箱。
- **入口**：工作室管理员和日常运营在订单区的第三个标签“艺人账目”；没有订单区的账号（经纪人）在侧栏有独立的“艺人账目”。

## 增补：L3-13 实现约定（2026-10-01）

- **迁移 0062**：
  - 登记 `idols.private`（`ON CONFLICT DO NOTHING`：跑过 `sync-roles` 的库里已有）。
  - 三张只追加的表：`artist_private_notes`（每次保存一个版本，按艺人连续编号）、`artist_private_note_accesses`（每次查看一张最长五分钟的收据）、`artist_private_note_confirmations`（解密后的复核）。
  - 数据库函数 `artist_private_note_authorized`：持 `idols.private` 的有效会话，且这个会话的内置登录记录 `second_factor` 是 `TOTP` 或 `RECOVERY_CODE`，且账号**现在**仍绑定了 TOTP。保存、查看收据、复核三处触发器都调用它，并核对各自的审计（`ARTIST_PRIVATE_NOTE_SAVED`、`ARTIST_PRIVATE_READ`，字段类别 `ARTIST_PRIVATE`）。
  - down 在已有备注或查看记录时拒绝（55000）。
- **两步验证门槛的边界**：
  - OIDC 会话没有内置登录记录，一律不能看；
  - 登录后才绑定验证器的会话，要重新登录一次；
  - 自助关闭两步验证只撤销其他会话，所以门槛同时看账号现状：关掉后当前会话立即看不到，已准备好的读取也不能复核。
- **加密**：四个字段合成一个带版本号的 JSON，用一个信封加密。新加密用途 `ARTIST_PRIVATE_NOTE` 按订单备注的独立扩展写法，不动冻结的 v1 枚举；信封绑定版本自己的 id。应用层先确认门槛满足才加密。
- **保存**：版本 id 由页面每次尝试生成，重发同一 id 返回已保存的那一版；页面开始编辑时的版本号与当前不一致时拒绝（`STALE_VERSION`），页面显示最新内容并请用户重新修改。
- **接口**：`/api/v1/admin/artist-notes/{context,read,save}`，本地体验组装与正式组装都挂上；`SECOND_FACTOR_REQUIRED` 映射为 403。上下文只返回门槛状态和版本列表（谁、什么时候），不含内容。
- **界面**：艺人编辑页底部、删除区之上的折叠区，只对持 `idols.private` 的账号出现（上下文被拒时整个区域不渲染）。
  - 打开才读取当前版本；历史版本逐个点开，每次都写审计。
  - 关闭、切走标签页或离开页面即从页面清除内容；草稿不存浏览器。
  - 不上传证件照片。
- **长度上限**：真实姓名 200、联系方式 2000、身份信息 2000、其他 4000 个字符。

## 验证与回退

- 验证：每个条目先写失败测试；实际 PostgreSQL 专项脚本覆盖越权反例（经纪人读改他人或未分配艺人、读他人留言、访问礼物/订单/备注；运营改派或读备注；未两步验证的超管读备注）；账目金额核对（币种分开、退款扣减、拒付整单、一单多艺人、未付款与取消不计入）；导出内容与页面一致且不含粉丝个人信息；七语言双端浏览器验收；`check:dev`；部署 stg 复核。
- 回退：三个迁移各自可 down（有归属、备注历史时拒绝回退，避免静默丢数据）；代码回退到上一版本即恢复为两个标准角色。经纪人账号可先暂停再回退。
