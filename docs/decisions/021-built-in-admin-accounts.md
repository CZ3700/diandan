# ADR-021：后台首发使用内置账号密码登录，两步验证由账号自行绑定

- 状态：Accepted
- 日期：2026-09-29
- 用户依据：用户明确要求"后台正式登录就用我们自己在服务器创建初始管理的账号密码就行了，设计一个正规的登录页面"；并决定"直接用账号密码登录，然后登录进去后多一个设置选项可以绑定 2FA，然后扫码绑定 2FA 来验证，并且还要有更改密码这些功能"。
- 执行：Claude（Windows 端），进度条目 L3-10。

## 决定

1. 首发后台身份源是平台内置账号（登录名 + 密码），不依赖外部 IdP。L3-05 的正式 OIDC 模式保留为可选接入方式，不再是上线前提。
2. 两步验证采用 TOTP（RFC 6238，兼容常见验证器 App）。账号登录后在"账号设置"里扫码自行绑定；绑定后，该账号每次登录都必须输入验证码。**不强制所有账号绑定**。会话记录本次登录是否经过两步验证。
3. "账号设置"提供：修改密码（需输入当前密码）、绑定和解绑两步验证（解绑需当前密码和验证码）、绑定时发放一次性恢复码。修改密码或解绑后，该账号的其他会话全部吊销。
4. 初始管理员和紧急访问由服务器命令完成：创建账号、重置密码、清除两步验证。密码只能交互输入，不出现在命令行参数、shell 历史或日志里。首发不提供邮件找回。
5. 保留的安全底线：
   - 密码用 `node:crypto` scrypt 加盐哈希，不存明文，也不能逆向；
   - 登录失败只给统一提示，按账号连续失败锁定，并按来源限速；
   - 会话、CSRF、RBAC、审计和吊销全部沿用现有机制，内置账号以平台专用 issuer 进入 `admin_identities`，角色和权限模型不变；
   - 登录成功、失败、锁定、改密、绑定和解绑全部写审计；
   - 退款、强制状态变更等二次确认保持不变。
6. 登录页按正式产品设计：品牌与黑金主题、账号密码表单、需要时的验证码步骤、清晰的错误与锁定提示、键盘可用，七语言界面。

## 兼容与后果

- 本 ADR 在首发范围内替代 SPEC §14"管理 API 使用 OIDC Authorization Code + PKCE"和 §15"管理员必须启用 MFA"，以及技术栈表"员工身份：标准 OIDC adapter + IdP MFA"。它也是 ADR-020 第 7 条"不放宽权限不变量"的一项由用户明确作出的例外。OIDC 登录路径本身不变，仍要求 IdP 证明 MFA。
- **已知风险（用户知情后接受）**：未绑定两步验证的账号只靠密码保护，一旦密码泄露或被撞库，攻击者可以退款、修改支付配置、查看粉丝私密留言。Claude 当时建议对所有账号强制两步验证，用户选择由账号自行绑定。缓解措施：
  - 失败锁定、来源限速和全量审计；
  - 账号设置页醒目提示尚未绑定；
  - 运营上建议有退款或财务权限的账号先绑定。
- 数据库需要新增内置账号凭据的迁移（0052 起），并放宽会话"必须经过 MFA"的约束，仅限内置 issuer；OIDC 会话的约束不变。
- 远程测试环境：新登录上线并验证后，撤掉后台前面的 Basic Auth，收件箱仍保留。
- 若以后需要强制两步验证，只需增加"该账号或角色必须绑定"的策略，不必改数据模型。
