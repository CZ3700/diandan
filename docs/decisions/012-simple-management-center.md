# ADR-012：单入口管理中心与原文直接发布

> 状态：Accepted for implementation — 2026-09-08 用户明确要求简化日常上传与上架
> Owner：Codex `/root`；任务 P3-06 内的可用性修正
> 关联：规范 3.0.0 §0.1/9.0；保留 ADR-006/009/010/011 的非冲突边界

## 决定

默认后台只有艺人、礼物和海报。运营上传一张图，填写实际需要的名字、描述、价格和分类后提交。内部身份、规格、图片加工、审计、发布传播及恢复由服务端负责，不要求运营处理技术字段、翻译包或多个角色窗口。

普通内容新增 `DIRECT_OPERATOR_V1` 发布模式与版本 3 的证明。真实授权运营可直接发布其原文；记录实际 actor/session、sourceLocale/hash、操作及媒体加工来源，不制造独立 reviewer 或七行 APPROVED 译文。旧严格证明和历史 hash 保留；政策、支付安全、邮件等关键内容继续严格模式。内容 provenance 单独版本化，不全局放宽购物车/订单的 LocaleContext v1。

原文先上线，翻译可选补充。原文容器使用真实 lang；缺少目标语言的详情页 noindex，不纳入该语言 sitemap/alternate。七语言 UI 保持各自完整；切换语言不改变价格、币种、市场、库存或支付状态。

同一原图生成手机、桌面等真实角色产物，原图/recipe/checksum 可追溯。默认完整展示加中性衬底，避免误裁和拉伸；不复制原图来伪造不同拍摄素材，不把插值当作更高原始细节。

提交是一项 PostgreSQL 中可恢复的操作。请求幂等、步骤有回执，后台处理有租约；队列不保存明文会话/CSRF/授权 token。推进敏感步骤前复核真实会话和权限。图片 I/O 在数据库短事务之外，最终内容与价格 head、审计及 outbox 原子提交。已提交但可见性确认失败时重试只确认结果，不能重复创建/发布。

价格和库存沿用权威表。默认市场、币种、履约和销售策略来自明确 PG 配置。可重复售卖为 PROCURE_ON_DEMAND，限量售卖写真实库存；礼物分类不推导库存。所有可收礼艺人的适用规则由服务端维护，不能保存一次有限列表后漏掉未来艺人。

海报历史恢复复制历史媒体引用到新版本，重新验证实际素材和当前权限，不改历史、不回退无关首页字段。

## 验证

合同失败测试、真实 PostgreSQL 迁移及权限/幂等/冲突测试；真实签名上传、持续图片 worker、公开媒体读取和匿名 Storefront 查询。浏览器实际文件选择框验证艺人新增、礼物上架、价格/类别/无库存可售、海报替换与恢复、失败重试；覆盖双视口、键盘、reduced motion 和七语言界面。保留现有严格发布回归。

本阶段仍为本地开发环境；生产身份、支付、staging 和真实交付的后续门禁不因简化界面而完成。

## 增补（2026-09-27）：日常图片统一铺满展示

用户在远程测试环境发现，艺人照片上传后在前台大小不一。原因是上面"默认完整展示加中性衬底"：原图按原比例缩进角色画布且不放大，衬底直接烘焙在派生图里，所以横图、竖图、小图在同样大小的框里显得大小不一。用户决定：**前台统一按各展示位的最佳比例显示，礼物同样适用**。

- 日常管理中心（艺人、礼物、海报）的派生图改用构图方式 `COVER_ALLOW_ENLARGE`：
  - 按角色比例裁切铺满画布，艺人照片 4:5、16:9、4:5，礼物 1:1；
  - 原图小于角色母版时放大填满。
- 焦点按内容类型固定：
  - 艺人照片取 (0.5, 0.3)：人像的脸通常在上三分之一；
  - 礼物与海报居中。
  - 试过 sharp 的注意力策略，它会被手部、台阶等高对比区域吸走焦点，所以不用。
- 可追溯：构图计划里的裁切区域小于目标画布，即表示发生过放大。原图、metadata revision、recipe 与 checksum 的追溯不变。
- 严格发布模式（§9.2/§9.7）仍只用 COVER/CONTAIN，且不放大。
- 代价：
  - 横图做竖版、竖图做横幅时会裁掉边缘；
  - 很小的原图放大后会发虚，界面暂不提示。
  - 如需逐张调整，后续可在管理中心增加焦点微调。
- 已发布的旧图不会自动重生成：需要重新上传图片保存一次，或清空测试数据后重建。

## 增补（2026-09-28）：日常管理中心删除艺人与礼物

用户要求在日常管理中心删除艺人和礼物，并选择"只要永久删除"（不做暂停/恢复）。

- **删除 = 永久归档（`archived`）**：
  - 数据库在触发器层面禁止物理删除艺人、礼物与规格（迁移 0019/0020），且归档后不能再改回；
  - 规范 §9.2/§9.3 也要求被订单引用后只能归档或下架；
  - 每次日常保存都会写入只追加的发布记录，所以物理删除不可行，也不应该做。
- **实现路径**：复用高级工作区已有的身份状态写入：艺人用 `idol-status`，礼物用 `gift-status`。它们同步执行、幂等，写审计和回执。不是日常管理操作，不经队列（队列是为图片处理设计的，归档没有图片工作），因此不需要新迁移。原因代码 `DAILY_CENTER_DELETE`。
- **权限不扩大**：
  - 删除艺人需要 `content.edit` 且覆盖全部 7 种语言；
  - 删除礼物需要 `gift.manage`（从商品上下文读取）。
  - 没有权限的账号看不到删除区。文档中的"日常运营"角色没有 `gift.manage`，因此不能删除礼物；需要时另行调整角色。
- **确认方式**：编辑页底部的删除区，要求逐字输入名称（忽略首尾空格与 Unicode 组合差异），然后点"永久删除"；页面不提供撤销。
- **删除后的行为**：
  - 从前台所有位置（目录、详情、SEO、首页推荐位）和日常列表中移除；
  - 历史订单读取的是自身快照，不受影响；
  - 购物车里已删除的礼物或艺人，只让对应那一行显示为不可用。
- **首页主视觉**：主视觉艺人继承自首页模板，日常管理中心不能更换。所以主视觉艺人被删除时，首页照常显示海报，只是不再链接到该艺人。主视觉的其他任何校验失败仍然整页失败（fail closed）。
- **规格不归档**：礼物本身的状态已经决定所有公开读取；而礼物归档后数据库不再接受规格回执。
- **只读礼物**：由严格模式创建、日常管理中心只读的礼物，仍只能在高级工作区删除。
