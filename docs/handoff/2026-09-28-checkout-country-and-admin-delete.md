## 关键决策及理由

1. **"与国家无关"的判定标准：选不同国家时看到的支付方式是否不同。**
   - 远程环境只发布了 `US` 一个国家，泰国粉丝原来只能选"美国"。这一步既不筛选任何东西，又让人困惑。
   - 只有一个可选国家，或所有通道覆盖相同国家时，都自动带出。
   - 自动带出的国家取已发布规则里排序后的第一个，确定性，不看语言或 IP。它只用于路由和创建回执（`payment_create_receipts.country`），不代表粉丝所在国家，也不发给 PSP（Stripe/Airwallex 创建付款时本来就不带国家）。规范 §5.7 已写明。
   - 适配器层按国家变化的能力不在判断范围内。国家限定以路由规则为准；通用网关如果按国家区别对待，运营应在路由规则里限定。
2. **T-8 为什么不在 API 端自动换新凭证**：原有测试和设计明确要求"已过期的会话只清除一次，不隐式替换购物车"（`cart-route.test.ts`）。所以由客户端显式重试一次。读操作不清 Cookie，是因为付款后的回跳页要凭这个 Cookie 读取结账会话、换取订单访问权（只有付款的那个浏览器能直接打开订单）。
3. **T-9 删除 = 归档，复用高级工作区的状态写入，而不是新增日常操作。**
   - 数据库触发器禁止物理删除艺人、礼物和规格（0019/0020），归档后不可逆；规范 §9.2/§9.3 也要求被订单引用后只能归档。
   - 日常操作流水线是异步队列，为图片处理设计。归档没有图片工作；若新增操作意图，要改 0022 的多处 SQL 守卫和目录快照，成本高，而现成接口已有审计、回执和幂等。
4. **权限不扩大**：删除艺人需要 `content.edit` 加全部 7 种语言，删除礼物需要 `gift.manage`（会话里没有这项，要从 `commerce-context` 读取）。没有权限的账号看不到删除区。文档中的"日常运营"角色没有 `gift.manage`，所以删不了礼物；远程环境的经理账号权限齐全。
5. **首页主视觉**：主视觉艺人继承自首页模板，日常管理中心改不了。如果删除时拦截，这位艺人就永远删不掉。所以改为兼容：仓储层只在"主视觉艺人已归档"时把主视觉槽位降级为不可用，前台照常显示海报、去掉艺人链接。其他任何主视觉校验失败仍然整页失败（fail closed），不降低内容校验强度。
6. **不改的地方**：
   - 结账预检遇到已删除礼物仍返回 `CONTENT_UNAVAILABLE`。它和 `GIFT_UNAVAILABLE` 在前台显示的是同一句话，而购物车已经把那一行标成不可用。
   - 礼物规格不归档：礼物状态已经决定所有公开读取，而礼物归档后数据库不再接受规格回执。
