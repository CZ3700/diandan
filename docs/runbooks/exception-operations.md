# 管理中心：待处理

进入管理中心的“待处理”，选择分类，点击“查看”。详情会显示当前状态、允许的下一步以及不能操作的原因。选择处理原因、勾选确认后提交，再读取最新状态。

| 分类 | 可执行操作 | 处理边界 |
| --- | --- | --- |
| 支付事件 | 重新处理已验证事件 | 使用数据库中已验证的标准化事件和原业务幂等标识；不上传或编辑 webhook 原文 |
| 重试失败 | 重新处理原队列任务 | 保留原事件、原消费者和历史记录；只允许已注册且具备可靠幂等保证的处理器 |
| 支付待确认 | 向原支付渠道核实 | 查询原账户与原支付尝试；不创建新扣款，不手动设为支付成功 |
| 通知失败 | 按现有受控规则重发 | 仅允许确定失败且仍符合条件的通知；已发送、结果不明、被后续通知替代或收件资料不可用时显示限制 |

提交后若提示“结果尚未确认”，使用“恢复原请求”。系统会沿用同一操作者、同一请求正文和同一幂等键；不要为了绕过提示不断创建新请求。状态已经变化时重新读取详情；权限被撤销后由有相应权限的人员继续处理。

“已受理”只表示操作与审计已保存。后台处理结束前显示处理中；恢复任务失败后保留历史并重新成为待办。核实支付与发送通知的最终结果来自原有持久流程，不能把管理中心按钮的回执当成资金或投递成功。

默认只显示仍需处理的记录。确定失败的通知在受控重发成功后退出默认列表，原失败和重发记录仍可在“全部记录”中查看；发送结果不明的记录不会因为出现后续记录就被隐藏。

## 维护约束

- PostgreSQL 是待办与处理记录的真相源。恢复操作租约到期后可由下一进程领取，旧代次不能覆盖新进程结算。
- 原 webhook effect、订单/退款/履约应用回执、outbox consumer 与通知去重记录必须保留；不得通过删除队列、清空效果记录或重置通知终态来“修复”失败。
- 队列恢复只处理原有业务效果，不运行动态代码。新增消费者应先具备持久幂等保证并完成对应验收，再纳入允许列表。
- 本功能不提供敏感 webhook 原文下载或查看入口。列表、详情、审计与诊断不包含私密留言、完整联系人、凭据或 PSP 原始报文。
- 只读权限与各类操作权限分别检查；支付核实和通知处理继续要求原有金融与通知权限。

实际命令和本轮证据见 `docs/progress/phase-5-operations-payments.md` 的 P5-06 执行卡。TEST 环境验证不替代真实供应商、商户及部署环境验收。

## 本地复验

在仓库根目录运行，使用项目固定的 Node 24.20.0 和 pnpm 11.25.0：

```sh
mise exec node@24.20.0 -- corepack pnpm --filter @fan-support/persistence-postgres test:postgres:admin-exceptions
mise exec node@24.20.0 -- corepack pnpm --filter @fan-support/api test:postgres:admin-exceptions
mise exec node@24.20.0 -- corepack pnpm verify:admin-exceptions:browser
mise exec node@24.20.0 -- corepack pnpm check:dev
```

实际数据库脚本使用独立临时资源。需要使用本机 PostgreSQL 时，HTTP/浏览器命令以 `ADMIN_EXCEPTIONS_TEST_POSTGRES_BIN` 指定 PostgreSQL 18 的绝对 `bin` 路径，持久层命令追加 `--native-bin /absolute/postgresql/bin`；本轮验证使用 18.6。HTTP/浏览器流程同时启动本仓库的 TLS TEST OIDC、对象存储、PSP 和邮件接收端，退出时清理自己创建的资源。浏览器检查与 `check:dev` 顺序运行，避免 Next dev 和生产构建争用生成目录。

这些命令用于开发验收，不是长期保存用户内容的启动入口。完整体验入口仍按 `local-experience-readiness.md` 交付。
