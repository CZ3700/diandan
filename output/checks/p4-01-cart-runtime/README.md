# P4-01 cart persistence and migration evidence

This scope implements the cart persistence port and its PostgreSQL adapter. It does not implement checkout, inventory reservation, cart editing or deletion. The parent task owns Application orchestration, KMS and HTTP composition.

- `cart-runtime-data.ts` maps strict internal records, preserves PostgreSQL microseconds, and resolves all supplied pepper candidates in one locked query. No match and ambiguous matches remain distinct failures.
- `cart-runtime-repository.ts` requires transaction-local credential authorization for item/receipt reads, checks real expiry and exact cart version again before append, writes the item and encrypted intent on the shared client, and records the current presentation locale without changing market/currency. Empty anonymous content has NULL message/name and a real wrapped key supplied by the KMS port; it is not a fabricated message ciphertext.
- `postgres-persistence.ts` supplies cart, current storefront proof, idempotency and outbox repositories through one SERIALIZABLE transaction manager. The Application must validate the current proof and write the corresponding outbox event before commit.
- Migration 0023 extends structural recipient consistency to explicit eligibility OR the immutable `ALL_ACTIVE_ARTISTS` rule, and fixes the existing NULL/PENDING moderation early-return defect. Automated evidence and privacy/history predicates remain intact. Current active/accepting/proof checks belong to the current commerce read, not the historical consistency trigger. Down refuses dynamic-only ownership or existing PENDING intents; it never deletes history or invents eligibility/approval.

Current checkpoint: the final catalog roundtrip is **23 migrations / 159 tables / exactly two changed function definitions**. The seventh real HTTP run passed **6,029 assertions / 1,905 setup requests**, including three separate fresh publish → first add cases with zero public pre-reads and both downgrade refusals. The fourth run's `CONTENT_UNAVAILABLE` remains unexplained; later passes are not a diagnosed fix. Full-workspace acceptance remains parent-owned and is not claimed here.

## Real initialization parameter regression

The first two actual HTTP attempts failed; the second localized request 1 (`POST /api/v1/carts`) to PostgreSQL `42P08`. `postgres-cart-runtime-parameters.mjs` then reproduced the same failure by preparing the actual repository SQL in an isolated database with all 23 migrations (`pg-parameters-red.log`). The INSERT SELECT expression and its WHERE expression inferred incompatible types for the same `$7` timestamp parameter. The fix adds the same explicit `::timestamptz` cast to the SELECT expression; input values and all expiry/constraint checks remain unchanged.

`pg-parameters-green.log` records 14 actual PostgreSQL assertions: all seven repository SQL statements prepare, an actual initialization INSERT preserves six-digit expiry and equal creation/update timestamps, and an expired initialization writes no row. This narrow SQL probe does not claim to validate commerce proof or encrypted add-to-cart. The helper's initial query-count and timestamp-fixture mistakes are preserved separately as `pg-parameters-fixture-count-error.log` and `pg-parameters-fixture-timestamp-error.log`; neither is product RED evidence. Scoped formatter/lint pass, and the final three-file/17-test suite passes again in `pg-targeted-after-parameters-green.log`.

Five older PG harnesses were adapted to migration 0023: catalog-directory, publication-runtime and admin-catalog explicitly roll back 0023 to 0022 before their original downgrade sequences; existing history/purge-job preservation assertions remain. Content-draft and validation-time harnesses only update the full-up expected head. Their scoped formatter/lint pass and non-author review is ACCEPT; actual execution is delegated to the parent's full check, not claimed here.

## First encrypted add: pending moderation regression

The third actual HTTP attempt initialized successfully but failed the first add at deferred COMMIT (`23514`). Independent PostgreSQL reproduction then proved a pre-existing three-valued-logic error in `validate_support_intent_moderation_evidence`: the table requires `moderation_decision_kind = NULL` for PENDING, but `NULL <> 'AUTOMATED'` does not enter the early return, so the trigger incorrectly demands automated evidence.

`pg-moderation-red.log` records the exact PENDING COMMIT failure and safe `AUTOMATED_EVIDENCE_REQUIRED` marker. The probe clones the actual support-intent columns/defaults/checks into a temporary table and attaches the installed deferred trigger; it deliberately does not claim to cover the real foreign-key/cart/outbox graph. `pg-moderation-green.log` records three actual assertions: PENDING without a fabricated decision/evidence commits, AUTOMATED without exact evidence is still rejected, and the rejected row is rolled back.

Migration 0023 also replaces that function with the single condition change to `IS DISTINCT FROM 'AUTOMATED'`. Every automated evidence/version/hash predicate remains exactly unchanged. Down restores the exact original function and additionally refuses existing PENDING intents, protecting their future legal updates from the old NULL defect. `migration-catalog-moderation.log` records a second actual 23-migration / 159-table up/down/up PASS. The final catalog diff has exactly **two** changed function definitions; the earlier one-function result remains historical evidence.

The final scoped suite is three files / 18 PASS (`pg-targeted-moderation-final-green.log`), with scoped formatter/lint PASS. The intermediate 17/18 result is preserved: its no-DML test mistook the original function's `TG_OP = 'INSERT'` string for an INSERT statement; the test now excludes the two separately byte-verified function definitions and forbids DML/EXECUTE outside them. Non-author review accepts the NULL fix, PENDING downgrade protection and the two rollback-proof modes without rerunning them.

`verifyCartRuntimeRollbackProtection` accepts `mode: 'PENDING' | 'DYNAMIC'` (default DYNAMIC). PENDING requires real explicit-recipient pending intents and zero dynamic-only intents before checking its exact rejection message. DYNAMIC requires real dynamic-only ownership and its own exact message. Both modes verify direct SQL and normal-runner refusal and unchanged counts/hashes for all six tables.
