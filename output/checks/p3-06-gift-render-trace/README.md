# P3-06 礼物页绘制追踪

本检查点承接 `0fd6fd0` 的读取一致性改动。上一轮 36 份有效报告未达到性能预算，中文模拟 LCP 两轮较慢，三个实际呈现间隔尚未解释。本轮不替换这些历史结果。

## 预先固定的实验

- 同一真实 PostgreSQL、TLS S3、媒体 worker、API seed，旧入口和当前入口各测中文礼物页三次，总六次。
- 旧入口是 `587b3a2` 的 `gift-detail-page-reads.ts` 与 `gift-seo.tsx`；其余生产输入保持 `0fd6fd0`。当前共享读取 helper 在旧入口中未被引用。
- 固定 Lighthouse 13.4.1、既有 mobile/simulate/slow-4G/CPU 设置、Chrome 启动参数和同导航内容审查。不额外预热、重试、筛样或调整预算。
- 每次保留 LHR、完整 artifacts、Trace、DevTools log、HTML、配置和原生读取窗口。两组之间不运行发布或回退操作；直接读取公开 API 的证明另存。
- 只追踪虚构 TEST 公开礼物页；原始文件在本地保存。正式七语言性能矩阵、RUM、真机、读屏、运营及商户验收不在本诊断结论内。

`comparison-plan.json` 在执行前固定组别、次数和两份入口的 SHA。`initial-source.json` 复核上一检查点的 2,212 项输入完全相同。后续源码记录使用对已提交 manifest 的可重建差异，避免重复提交完整清单。

两组来自 `output/checks/p3-06-storefront-acceptance/run-2026-09-17T04-12-40-212Z/browser-attempt-{1,2}/gift-render-trace/`。采集四文件在两组间未变，分析工具在全部采集结束后补齐输入绑定，再运行离线重放；其开发期指纹变化不影响两组浏览器输入。最终所有原 2,212 项输入与 `0fd6fd0` 相同，只新增六个诊断脚本/测试文件。
