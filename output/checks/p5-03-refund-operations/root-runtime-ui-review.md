# P5-03 runtime / management UI integration review

Reviewer: Codex `/root`, author of shared contracts/domain and fulfillment guards, not author of finance application/API/worker or management finance UI. This review applies to the local TEST implementation; it does not approve commercial merchant refund behavior or production deployment.

## Source review

- API transport retains the existing private endpoint envelope, CSRF/session checks, fixed operation mapping, strict Zod parsing and response-to-command binding. A browser cannot nominate a provider/account or inject an actor, session or internal action. Application repeats receipt target validation across its port boundary.
- Durable mutation acceptance commits a permanent receipt before optional provider work. A failure after acceptance does not claim that money moved or invent a second command. The recovery runner claims ownership in PostgreSQL before external I/O, then settles separately. It dispatches only the four allowed operations and uses the persisted original provider/account binding.
- An adapter exception or malformed/mismatched result becomes uncertainty. An accepted mutation may immediately query its result; that second claim must be reconciliation. Financial finality still requires authenticated query or verified webhook evidence and canonical ledger application. Worker recovery and webhook application reuse the same application/port boundary.
- The existing management center receives an order finance panel and a paginated reconciliation view. There is no separate merchant console or new public payment authority. Read-only roles cannot submit mutations; server-side finance permission remains authoritative.
- Refund input uses currency-aware integer minor units, item-level allocation, exact total validation, order version, reason and explicit confirmation. The display separates successful refunds from pending capacity rather than counting successful money twice. Pending refunds and OPEN/LOST disputes pause fulfillment; WON can follow the existing eligible workflow.
- The browser stores only the tab-local pending command and idempotency key scoped to authenticated actor and order. Storage must successfully persist and read back before dispatch. Reload and uncertain responses retain the same key; no credentials or private fan content enter this store. Keyed order-detail lifecycles and request epochs prevent stale detail responses from replacing the current order.
- Financial user copy has all seven locales and remains in the strict DRAFT review manifest. Local automation proves layout and interaction, not human translation approval. Confirmation focus and instant scrolling respect reduced-motion preferences.

The partial-refund event-lifetime finding is closed: the handler captures its value synchronously, the real deferred-handler regression first failed and now passes, and the final actual browser filled both amounts consecutively and completed the request. Duplicate gift names include a line position and artist snapshot. The undefined spacing token and named switch-container semantics were also corrected and verified in the accepted screenshots. Earlier receipt-target, pending-capacity, query-audit and lease findings have explicit regressions and independent persistence review.
