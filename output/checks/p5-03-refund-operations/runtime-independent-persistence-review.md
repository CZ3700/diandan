## Findings and resolution

1. **Original attempt recovery could remain stuck after replacement.** Earlier claim used `order.current_payment_attempt_id` and threw if it differed from the durable operation's attempt. A failed old manual payment reconciliation could therefore keep blocking the due queue after an ordinary replacement payment. The storage author now loads `op.attempt_id` constrained to the same order (`admin-finance-data.ts:35`); a superseded, trusted failed/canceled/expired attempt records `FINANCE_OPERATION_SUPERSEDED` and completes only the old operation (`admin-finance-recovery.ts:24`). A nonterminal old attempt is not silently abandoned; cancellation's storage guard prevents a replacement while its intent is active. Evidence for a different current attempt is recorded for review instead of mutating the replacement.

2. **A query whose process died before settlement had no durable attempt audit.** Earlier code reserved a result audit ID but wrote the audit only after an authenticated response or failure. The storage author now appends `FINANCE_RECONCILE_DISPATCH_AUTHORIZED` in every reconcile claim transaction (`admin-finance-recovery.ts:93`). This means authorization to dispatch, not proof that the PSP was contacted. Settlement still creates a distinct `PAYMENT_PROVIDER_RECONCILE` result audit; only a valid authenticated result can become financial evidence. Stale responses cannot manufacture result audits. The storage fixture explicitly tests loss of lease while waiting for both operation and order locks, preserving the earlier dispatch authorization.

3. **Receipt target validation was incomplete in reviewer-owned code.** Application/API originally compared only the order. A mutation receipt for the wrong refund on that same order could pass the boundary. Added RED tests, then required REFUND to return a non-null refund ID, CANCEL to return null, and refund RECONCILE to return the exact requested refund ID. See `admin-finance-context.ts:52` and `admin-finance-route.ts:14`. This is a self-review correction, not an independent persistence finding.

## Invariants inspected

- **Money and capacity:** `validateFinanceRefund` holds the order and attempt before querying the complete refund set; it uses `BigInt` for aggregate and line capacity. Every non-FAILED refund, including REQUESTED/SUBMITTING/PROCESSING/UNKNOWN and completed money, consumes capacity. Request currency equals the capture currency, allocation sums/unique items are contract checked, and the original capture ledger must exist. The database also guards amount totals, allocations and complete projections.
- **Dispatch versus proof:** A claim commits phase, generation and lease before external I/O. A successful refund create response only authorizes an immediate new reconcile claim. Adapter exceptions or invalid/mismatched responses preserve uncertainty. Only provider resolution failure _before calling an adapter_ permits the same immutable refund/cancel command to regain dispatch authorization. A possibly submitted refund is never resubmitted by recovery.
- **Locks and fencing:** Commands that can touch existing operations acquire payment-runtime operations then finance operations before cart/order/attempt locks. Evidence application uses that same operation-first order. New refunds acquire cart/order/attempt before their newly created operation and do not wait on an existing finance operation. Claims and settlement own the finance operation first. PSP calls occur outside every database transaction. The updated repository rechecks lease liveness after operation-lock and aggregate-lock waits. No additional concrete reverse-order cycle was found in the inspected finance paths.
- **Evidence and canonical ledger:** Provider account, environment, external payment reference, currency, refund/dispute reference, amount and native transaction identity are checked. The economic transaction bridge supports the same native REFUND across webhook and authenticated query while retaining both observations. OPEN/LOST observations of one native chargeback share the economic transaction. An event cannot rewrite an already recorded financial terminal outcome. Repeating a successful authenticated query still creates its own result audit even when its provider event already exists.
- **Projection and original payment:** Refund/dispute application does not turn a SUCCEEDED payment attempt into a failed one. Successful refund totals project partial/full refund in the same transaction; the complete dispute set projects the order dispute status. The private application receipt and outbox history make repeat worker delivery idempotent. Unknown capture association stays pending; incompatible evidence produces a review record.
- **Authority and fulfillment:** Read access reuses `orders.read`; mutation requires separate `finance.manage`, live MFA session, CSRF, confirmation, reason, version and permanent actor/action/key receipt. Pending refunds pause preparation/delivery. OPEN/LOST disputes reject new refunds without occupying capacity or calling the PSP. Cancellation releases inventory/cart only after local no-call proof or trusted terminal failure/cancellation evidence.
