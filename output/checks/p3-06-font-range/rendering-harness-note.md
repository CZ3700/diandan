# Fallback rendering harness isolation correction

The first real browser attempt remains an original **FAIL** at `rendering-attempt-b457083a-de4d-4d01-b7d6-b187976b8585/results.json`; its JSON and eight PNGs are unchanged. All 792 pixel/metric comparisons matched, all requested faces reported loaded, all 65 font response hashes matched, `errors` was empty, and both owned resources closed. These facts alone do not establish correct rendering: the CDP platform-font evidence showed Noto Sans JP custom fonts for both Japanese variants at all four weights (223 glyphs), but **PingFang SC system fonts** for both Chinese variants at all four weights (227 glyphs). The strict custom-font gate correctly rejected the attempt. Its Chinese pixel equality must not be used as evidence that the supplied Chinese fonts were preserved.

The source-level defect is shared font identity between sequential profiles. The first harness registered `TEST_baseline` and `TEST_candidate` for Japanese, then cleared the `FontFaceSet` and registered Chinese under the same family names while the previous profile's DOM probes still referenced those names. Unlike `scripts/fonts/verify-font-shaping.mjs`, the harness did not include the profile ID in its family aliases. Reusing family names couples font selection and any browser display/cache state across profiles; `FontFace.status === "loaded"` and `document.fonts.check()` did not prove which font painted the DOM. The particular Chromium optional-display/cache transition is a hypothesis supported by this sequence and the CDP discrepancy, not a separately traced browser-engine fact.

The bounded correction makes the family identities disjoint: `TEST_japanese_baseline`, `TEST_japanese_candidate`, `TEST_simplified-chinese_baseline`, and `TEST_simplified-chinese_candidate`. Registration, explicit loading, DOM probes and canvas drawing all use the same profile-specific identity. Returned loaded faces must additionally match that identity, and the report records it. The corpus, source CSS/font bytes, source ordering, optional display policy, weights, dimensions, zero pixel/metric tolerances and the CDP `isCustomFont` requirement remain unchanged. No production source changed, and there is no retry or failure replacement in the harness.

This note records the correction before its browser rerun. Scoped syntax, ESLint and Prettier checks are run separately; they cannot establish browser success. Root will execute one new attempt after coordinated browser work ends. Success requires all 792 comparisons and custom-font checks for both profiles, plus input/response hash checks and owned cleanup. A new failure remains a failure; the original attempt stays retained regardless of the new outcome. This is a rendering diagnostic, not a performance sample or a formal navigation/RUM gate.
