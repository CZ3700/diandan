## Isolation, cleanup and interpretation boundaries

- The fixture registers each owned resource immediately, cleans them in reverse order, continues after individual close failures, and rejects the overall operation on cleanup failure. Browser contexts/browser/Chrome, viewer sockets/sessions/upstream agent, read pool, API, workers, TLS gateway and fixture PG client have owned close paths. PG native cleanup verifies its marker/data directory; Docker/S3 cleanup verifies generated names/labels. No global process or user-instance cleanup is introduced.
- **Use the full command outcome, not one intermediate JSON file, as cleanup evidence.** `catalog-performance-runner.mjs:216–233` writes its measurement PASS before `persistence.close()`. The outer catalog summary catches that failure, but `apps/api/scripts/catalog-performance.mjs:89–92` writes its overall child PASS after PG/fixture cleanup and before the parent S3 harness has completed. A later S3 cleanup error makes the command fail while that JSON can still say PASS. The parent must retain exit status and owned-resource cleanup evidence, as planned; the child JSON alone does not certify all resource cleanup.
- The existing shared S3 runner timeout uses SIGKILL. Such forced termination bypasses child `finally` blocks, so the normal cleanup guarantees do not cover timeout/forced-kill cases. A timed-out attempt is failed evidence and requires verification of its exact owned PG/Next resources before a new measurement. Do not touch the user's original instance.
- Each evidence run needs a fresh owned output directory and the parent’s frozen isolated source workspace. The catalog CLI permits an existing directory, and the browser fixture builds into its supplied workspace’s `.next`; the orchestrator's isolation/fresh-directory discipline is part of reproducibility and protection of the existing user instance.
- Catalog `status: PASS` means complete successful cost observation with preserved proof reads. `allWithinCurrentBffTimeout` is a separate observation, and 8 seconds is explicitly a failure ceiling, not a newly invented performance target. Likewise, no local Lighthouse or catalog result proves SPEC real-user p75 LCP/INP/CLS.
