## Follow-up diagnosis before final freeze

The author’s native-tab experiment (`rum-lifecycle-native-green.json`) established visibility and three header-level 204 observations using an independently owned Chrome/profile and `chromium.connectOverCDP(..., { noDefaults: true })`. The locked Playwright 1.62.1 public `ConnectOverCDPOptions` documentation explicitly states that this option omits focus/default media emulation for the existing default context and does not affect new contexts. Accordingly the revised harness uses a fresh owned default context for each positive and excluded document, then measures its actual viewport. This is a supported test configuration, rather than patching Playwright internals or dispatching synthetic visibility events.

That first native-tab GREEN did **not** yet prove completed response transport. The subsequent retained `rum-lifecycle-regression-1/2/3` failures showed validated 204 headers followed by `net::ERR_ABORTED`; waiting for `response.finished()` correctly kept the stricter harness failing. These failed attempts remain evidence and are not relabeled as complete integration.

Read-only inspection found no cancellation operation in `observeRum`: it listens and reads request headers/body/status/completion, without routing, aborting, fetching or consuming response bodies. The actual product sender discarded successful Responses and only handled rejection. The author then isolated this separately from web-vitals, visibility, Next, and the RUM observer: `rum-transport-consume-probe.json` records that plain-204 `void fetch().catch()`, awaiting only status, and a status-only `.then()` all produce a post-204 abort before cleanup, whereas consuming the empty body with `text()` or `arrayBuffer()` produces both CDP and Playwright completion.

This is consistent with the [WHATWG Fetch Standard §5.7](https://fetch.spec.whatwg.org/#garbage-collection), which permits ending an ongoing fetch when the termination is not observable through its arguments/return value and distinguishes unobserved bodies. It does not prove Chrome's internal GC cause without additional tracing. The controlled comparison is sufficient to identify the response-consumption difference; the observer must retain its failed-request checks instead of adding an abort whitelist.

Independent cleanup review also identified and reported two real helper defects before freeze: `await launcher.launch()` could reject after spawning without returning its handle, and the locked launcher's synchronous `kill()` neither waits for exit nor propagates system kill errors. The revised direction keeps the Launcher before startup, bounds browser disconnection and exit verification, continues cleanup after errors, and retains the profile when process exit is unconfirmed. Final source/tests remain under review; original entry conditions above are still pending full real-site acceptance.
