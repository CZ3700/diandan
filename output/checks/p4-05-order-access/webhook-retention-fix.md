# Webhook payload retention clock boundary

Owner: `/root/access_postgres`. Root authorized this narrowly scoped production correction after the second full quality gate reached the old order-payment webhook suite and repeatedly failed with a redacted SQLSTATE 23514 at `reliable-event:insert-webhook-payload` / `webhook_payloads_retention_check`.

The application authorizes an absolute expiry based on its receive time plus seven days. The original 0005 table anchors payload `created_at` to PostgreSQL `transaction_timestamp()` and requires `created_at < retention_expires_at <= created_at + interval '7 days'`. When the application clock leads PostgreSQL, forwarding its seven-day expiry directly can exceed that immutable database ceiling. The original payload trigger also requires exact transaction time, and the original inbox trigger requires its `received_at` to equal the payload creation time, so moving `created_at` or using a wall-clock retention ceiling would violate existing receipt semantics.

Only one production SQL expression changed in `packages/persistence-postgres/src/reliable-event-repositories.ts`: the retained expiry is now `least($6::timestamptz, transaction_timestamp() + interval '7 days')`. It never exceeds the caller's absolute authorization, preserves a shorter authorized expiry exactly, and leaves the original lower-bound constraint to reject already expired/equal-to-created input. The parameters, occurrence time, signature time, receipt time, identity/concurrency handling and encrypted payload are unchanged. No migration, trigger, retention allowance, sleep or clock setting was changed.
