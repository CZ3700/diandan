# Order access PostgreSQL checkpoint

Owner: `/root/access_postgres`. Base: `ab0b137`. This is a P4-05 subtask, not a new task or release approval.

The existing `0004` token/session model remains authoritative. Both tables retain immutable digests, pepper versions, order scope, expiry, and append-preserving state transitions. A token can move from `ACTIVE` only once. A session references exactly one consumed token, and each order retains at most one `ACTIVE` token and one `ACTIVE` session. Expired rows must be transitioned before replacement; wall-clock expiration alone does not remove a row from these partial unique indexes.

`0028_order-access` adds only a keyed rate-limit counter and an append-only access audit. It does not change migrations 0001–0027 or add financial/notification state. The audit enforces ownership among order, token, and session; raw credentials and request bodies are never audit values. Populated counters or audits prevent rollback because dropping them would erase authoritative access evidence or reset enforcement.

## Transaction design

- Resolve candidate ownership without holding token/session locks, then lock the canonical cart and order, then reselect the token/session under lock. No operation locks a token first and later waits for its order.
- Issuance uses an internal order reference and trusted processing context. It accepts only a confirmed paid aggregate. Existing active credentials are expired or revoked atomically before creating the next generation and writing an audit.
- Checkout bootstrap proves the existing cart credential, converted/non-expired cart, exact checkout/order ownership and confirmed payment. Quote expiry is unrelated to access to an already paid order. It issues and consumes an internal token and creates a session in the same transaction; the link credential is never returned to the browser.
- Exchange accepts only token digest candidates and the new session digest. Its token is rechecked for active status and actual expiry after locks. A consumed token cannot recover a lost cookie; it cannot issue another session. Transaction rollback preserves its original state.
- Revoke requires the public order identifier and a currently valid session for that exact order. It revokes active credentials and records the operation atomically, without a public internal-order-id administration entry point.
- Read checks actual session creation/expiry and scope on every request. It reads immutable order/order-item facts and current canonical fulfillment status. It never decrypts support intent or contact data and never invokes PSP, payment application, inventory, outbox or notification work.
- Rate enforcement is committed separately before authorization, including rejected requests. A PostgreSQL UPSERT serializes requests for the same scope/keyed bucket. No in-process map or Redis is introduced.
